# GrowHelper: стратегический план изменений

## Назначение

Этот файл фиксирует согласованный план развития GrowHelper.
Он описывает, что требуется изменить и зачем.
Он не заменяет нормативный `docs/BRIEF_v2.md`.
Главный принцип всех изменений — KISS.
Новые сущности добавляются только при прямой необходимости.

## Целевой результат

GrowHelper выглядит для пользователя как самостоятельный помощник по выращиванию.
Пользователь не сталкивается с внутренней identity Hermes.
Каждый предметный разговор относится к одному активному Plant.
Каждый Plant хранит собственную историю, фотографии и актуальное состояние.
Hermes остаётся внутренним runtime и не меняется на уровне core.
Существующие Profiles, Kanban и toolsets продолжают работать.

## 1. Публичная identity

- [ ] Закрепить в `SOUL.md`, что публичное имя агента — GrowHelper.
- [ ] Запретить представляться Hermes или универсальным агентом.
- [ ] Назвать Profiles, Kanban и tools внутренними деталями.
- [ ] Не упоминать внутренние детали без прямой необходимости.
- [ ] Зафиксировать короткий специализированный ответ «что умеешь».

### Зачем

Пользователь должен понимать назначение продукта с первого ответа.
Упоминание Hermes размывает позиционирование GrowHelper.

## 2. Предметные границы

- [ ] Закрепить выращивание как единственную рабочую предметную область.
- [ ] Разрешить общие вопросы о работе самого GrowHelper.
- [ ] Разрешить создание нового Plant и выбор существующего.
- [ ] Связывать растениеводческие сообщения с активным Plant.
- [ ] При неясной связи уточнять, к какому Plant относится сообщение.
- [ ] На явно посторонние вопросы отвечать согласованным отказом.
- [ ] Не ограничивать внутренние tools, полезные для растений.

### Зачем

Предметная граница удерживает долгий разговор вокруг реальных растений.
Уточнение Plant предотвращает смешивание историй и рекомендаций.
Полный полезный toolset сохраняет качество поиска и анализа.

## 3. Поведение до создания первого Plant

- [ ] Сделать первые ответы тёплыми и простыми.
- [ ] Объяснять назначение GrowHelper без внутренней терминологии.
- [ ] Предлагать начать с команды `/addplant`.
- [ ] Отвечать на вопросы о том, как устроена система.
- [ ] Не создавать Plant вне согласованного сценария.

### Зачем

У нового пользователя ещё нет предметного контекста.
Слишком строгий ответ на этом этапе мешает начать работу.

## 4. Определение Plant

- [ ] Закрепить единое пользовательское объяснение Plant.
- [ ] Использовать его в onboarding и ответах о системе.

### Смысл Plant

Plant — отдельная зона или контур выращивания.
Это может быть одна грядка, один подоконник или гидропонная установка.
В одном Plant могут находиться разные виды растений.
Новый Plant нужен для территориально или физически отдельной зоны.
Границей также служит самостоятельный источник питания или ухода.
Это относится к корневой и лиственной зонам.

### Зачем

Определение соответствует реальному уходу, а не ботанической классификации.
Оно помогает правильно разделять условия, историю и рекомендации.

## 5. Публичное меню Telegram

- [ ] Ограничить глобальное меню штатным `command_menu` Hermes.
- [ ] Показывать `/addplant` — создать новый Plant.
- [ ] Показывать `/plant` — выбрать существующий Plant.
- [ ] Показывать `/compress` — сжать текущий диалоговый контекст.
- [ ] Показывать `/new` — начать новую Hermes-сессию.
- [ ] Показывать `/status` — увидеть текущую модель и состояние сессии.
- [ ] Показывать `/context` — увидеть заполненность контекстного окна.
- [ ] Не добавлять `/help`.
- [ ] Не добавлять другие команды без отдельного решения оператора.
- [ ] Сохранить расширенный служебный доступ оператора.

### Зачем

Стандартное меню Hermes раскрывает лишние технические возможности.
Шесть выбранных команд покрывают управление Plant и диалогом.
`/status` и `/context` дают прозрачность без изменения настроек агента.
Лимит и приоритет меню скрывают лишнее без патча Hermes core.

### Важная граница

Меню управляет видимостью команд в Telegram.
Разрешение на выполнение команд задаётся конфигурацией Hermes.
Публичное меню и список разрешённых команд должны совпадать.

## 6. Выбор Plant через `/plant`

- [ ] Получать список Plant текущего Telegram-пользователя.
- [ ] Показывать их имена через одноразовую `ReplyKeyboardMarkup`.
- [ ] После нажатия делать выбранный Plant активным.
- [ ] Сразу убирать одноразовую клавиатуру.
- [ ] Присылать сохранённый аватар выбранного Plant.
- [ ] Подписывать фотографию коротким подтверждением переключения.
- [ ] При отсутствии аватара отправлять текстовое подтверждение.

### Зачем

Telegram не показывает динамический список аргументов slash-команды.
Одноразовая клавиатура решает выбор без отдельного интерфейса.
Аватар визуально подтверждает смену контекста.

## 7. Создание Plant через `/addplant`

- [ ] `/addplant` переводит диалог в onboarding нового Plant.
- [ ] Первым шагом GrowHelper просит фотографию для аватара.
- [ ] До фотографии не продолжать обсуждение нового Plant.
- [ ] Не привязывать ожидаемую фотографию к старому Plant.
- [ ] После фотографии создать Plant со статусом `onboarding`.
- [ ] Сохранить сжатую фотографию как его аватар.
- [ ] Дать короткий позитивный комментарий о фотографии.
- [ ] Затем предложить пользователю задать имя Plant.
- [ ] При отсутствии имени использовать первое свободное имя из списка.
- [ ] Сделать новый Plant активным.
- [ ] После onboarding вести разговор только в его контексте.

### Зачем

Фото даёт Plant узнаваемый визуальный образ с первого шага.
Статус `onboarding` отделяет создание Plant от полного описания условий.
Имя по умолчанию не позволяет сценарию зависнуть.

## 8. Обработка аватара

- [ ] Сжимать загруженную фотографию перед постоянным сохранением.
- [ ] Гарантировать итоговый размер не более 500 КБ.
- [ ] При необходимости уменьшать разрешение и качество кодирования.
- [ ] Сохранять качество, достаточное для узнавания Plant.
- [ ] Не хранить исходный тяжёлый файл аватара на сервере.
- [ ] Хранить путь к аватару в записи соответствующего Plant.
- [ ] Отправлять этот файл при переключении Plant.

### Зачем

Аватар используется часто, но не требует разрешения исходной камеры.
Ограничение размера сдерживает рост дискового хранилища.
Один обработанный файл проще хранить и повторно отправлять.

### Граница

Ограничение 500 КБ относится только к аватару Plant.
Диагностические фотографии остаются частью истории наблюдений.
Их политика хранения этой задачей не меняется.

## 9. Активный Plant и маршрутизация

- [ ] Хранить активный Plant отдельно для каждого Telegram binding.
- [ ] Подставлять его контекст в каждый предметный запрос.
- [ ] Не переносить сведения между Plant автоматически.
- [ ] При упоминании другого Plant предложить переключение.
- [ ] При двусмысленности задать один короткий вопрос.
- [ ] При постороннем вопросе напомнить о текущем Plant.
- [ ] Для нового контекста направлять пользователя к `/addplant`.

### Зачем

Активный Plant делает обычный разговор естественным и коротким.
Явное переключение защищает долгосрочную историю от смешивания.
Раздельная маршрутизация нужна для работы нескольких пользователей.

## 10. Долгосрочная память Plant

### Что сохранить

- [ ] `activity.jsonl` — точный публичный диалог и доставку сообщений.
- [ ] `photos/` — фотографии, относящиеся к Plant.
- [ ] `current-state.md` — актуальное состояние.
- [ ] `history-summary.md` — компактную долгосрочную траекторию.
- [ ] `journal/` — подробный рабочий журнал.
- [ ] `dataset/` — отобранные повторно используемые свидетельства.
- [ ] Kanban — задачи, зависимости и handoff между Profiles.

- [ ] Записывать события onboarding и переключения в историю Plant.
- [ ] Обновлять краткую память после значимых изменений.
- [ ] Загружать в контекст только память активного Plant.
- [ ] Не загружать полную переписку на каждый ход.
- [ ] Сохранять важное состояние при `/compress` и `/new`.
- [ ] Не создавать второй backend или зеркало Kanban.

### Зачем

Диалоговая сессия не должна быть единственным носителем знаний.
Сжатие контекста не должно стирать историю выращивания.
Компактные файлы дают достаточно фактов без лишнего контекста.

## 11. Profiles и Kanban

### Что сохранить

- [ ] Текущий постоянный состав Profiles.
- [ ] Инвариант `observation -> inference -> recommendation -> follow-up`.
- [ ] Минимальные Cycle только для содержательных событий.
- [ ] Раздельную ответственность специалистов.
- [ ] GrowHelper как единственную точку публичного ответа.

### Что не менять

- [ ] Не создавать новые роли.
- [ ] Не запускать reviewer для каждого запроса.
- [ ] Не превращать plugin в доменный backend.
- [ ] Не добавлять очередь, event bus или отдельную базу данных.

### Зачем

Текущий workflow уже покрывает анализ растений.
Новые Telegram-сценарии должны только правильно подавать ему контекст.

## 12. Запросы на изменение GrowHelper

- [ ] Не выполнять просьбы пользователей изменить GrowHelper.
- [ ] Коротко сообщать, что запрос передан оператору.
- [ ] Отправлять содержание запроса Telegram-пользователю `@dyingseed`.
- [ ] Использовать только заранее настроенный адрес оператора.

### Зачем

Пользовательский бот не должен заниматься собственной разработкой.
Оператор должен видеть реальные пожелания пользователей.
Фиксированный получатель сохраняет сценарий простым.

## 13. Источники истины

- [ ] Обновить `docs/BRIEF_v2.md` под продуктовый контракт.
- [ ] Обновить `SOUL.md` под identity, границы и тон.
- [ ] Обновить plugin под команды, onboarding и аватары.
- [ ] Обновить установщик и doctor под настройки Telegram.
- [ ] Не менять `team.yaml` шире необходимого.
- [ ] Не менять Hermes core.

## 14. Стратегия проверки

- [ ] GrowHelper не называет себя Hermes.
- [ ] Ответ «что умеешь» остаётся коротким и предметным.
- [ ] Посторонний запрос получает согласованный отказ.
- [ ] Публичное меню содержит ровно шесть команд.
- [ ] `/plant` показывает только Plant текущего пользователя.
- [ ] Переключение меняет активный Plant.
- [ ] `/addplant` сначала ожидает фотографию.
- [ ] Аватар после обработки не превышает 500 КБ.
- [ ] Тяжёлый исходник аватара не остаётся на сервере.
- [ ] Plant получает имя пользователя или имя по умолчанию.
- [ ] История записывается в правильный workspace.
- [ ] `/compress` и `/new` не уничтожают память Plant.
- [ ] Существующие Kanban-сценарии продолжают работать.

Перед deploy запустить основной regression suite и doctor. Telegram E2E выполняет оператор вручную; без наблюдаемого сообщения его нельзя считать проверенным.

## 15. Порядок реализации

- [ ] Обновить продуктовый контракт и `SOUL.md`.
- [ ] Затем реализовать Telegram-меню и доступ к командам.
- [ ] Затем реализовать `/plant` и визуальное переключение.
- [ ] Затем реализовать `/addplant` и обработку аватара.
- [ ] Затем связать новые события с памятью Plant.
- [ ] Обновить doctor и тесты, затем выполнить deploy-проверку.

Каждый этап должен давать отдельно проверяемый результат.

## 16. Что намеренно не делаем

- [ ] Не патчим Hermes core ради меню или callback-кнопок.
- [ ] Не создаём отдельный Telegram-сервис.
- [ ] Не создаём отдельный backend для Plant.
- [ ] Не добавляем базу данных, event bus или очередь.
- [ ] Не создаём отдельную session на каждый Plant.
- [ ] Не добавляем новые публичные команды.
- [ ] Не добавляем `/help`.
- [ ] Не убираем полезные инструменты выращивания.
- [ ] Не усложняем security сверх согласованного уровня.

## 17. Критерий завершения

Новый пользователь видит только GrowHelper.
В Telegram ему доступны ровно шесть согласованных команд.
Он создаёт Plant с фотографии и выбирает Plant одним нажатием.
Аватар не превышает 500 КБ и подтверждает переключение.
История и основные выводы сохраняются раздельно по Plant.
Посторонние запросы не уводят GrowHelper из предметной области.
Существующие Profiles, Kanban и tools работают, а изменения проходят тесты.
